# Architecture and engineering audit — 2026-09-02

## Executive assessment

The project has a credible product foundation and several good security and
quality practices: non-root runtime containers, authenticated API surfaces,
upload validation tests, Alembic history, structured production logging,
dependency scanning, frontend type checking, and an emerging shared consultant
knowledge layer. It is not yet at an enterprise review baseline because some
critical controls are documented or present but not reliably enforced.

This audit examined the current working trees, including uncommitted backend
and frontend changes. It did not modify implementation code. Findings are
prioritized by risk, not by ease of repair.

## P0 — release blockers

### 1. The root build cannot atomically contain or validate the frontend

Evidence:

- Root `.gitignore` excludes `frontend/` because it is a separate repository.
- The root Git index contains no frontend files.
- Root `.github/workflows/ci.yml` nevertheless defines a frontend job with
  `working-directory: ./frontend`.

Impact: a clean checkout of the root repository does not contain the frontend,
so its frontend CI job cannot run. Backend and frontend changes cannot be
reviewed, tagged, rolled back, or released atomically.

Decision required: either make a true monorepo by importing frontend history,
or formalize two repositories with independent CI and an explicit versioned
release contract. Do not leave the current hybrid state.

### 2. Production schema migration can silently fall back to `create_all`

Evidence: `backend/app/database.py::init_db` runs Alembic during application
startup and, after an Alembic exception on PostgreSQL, calls
`Base.metadata.create_all()`.

Impact: a failed migration can be masked by partial schema creation; existing
tables are not safely transformed; multiple API replicas may race migration;
and deployment health becomes coupled to schema administration.

Required outcome: run `alembic upgrade head` as a single controlled deployment
step, fail the release on error, remove the PostgreSQL `create_all` fallback,
and reserve `create_all` for isolated tests/local SQLite only.

### 3. Current CI has non-enforcing and likely invalid backend steps

Evidence:

- Mypy ends with `|| true`, so type errors cannot fail CI.
- The test step sets `working-directory: .` while installing `-e .`; the root
  has no Python project metadata.
- Tests default to `sqlite+aiosqlite`, but `aiosqlite` is absent from
  `requirements.txt` and CI's explicit tool install.
- Ruff checks `app/` only, not tests or formatting.

Impact: a green or partially green workflow is not evidence that the reviewed
backend is typed, installable, or tested.

Required outcome: separate runtime/dev dependencies, use deterministic install
commands, make every gate blocking, and prove the workflow on a clean checkout.

## P1 — high priority

### 4. Mutation authorization policy is inconsistent and under-specified

Evidence: GraphQL `create_crew_member`, `update_crew_member`, document upload and
confirmation, project creation/update/assignment, and certification mutations
mostly use `@require_auth`; deletion/verification use `@require_admin`. The REST
upload path requires admin. No resource-ownership policy is documented.

Impact: any authenticated user may be able to alter organization-wide or
sensitive records, and equivalent REST/GraphQL operations can apply different
policy.

Required outcome: define a role/operation matrix, enforce it in a central
policy layer, add negative authorization tests for every mutation, and audit
sensitive reads and writes.

### 5. Tests can touch real configuration and block on Redis

Evidence: settings are imported before tests fully isolate environment; the
first auth test calls the real Redis availability path for login throttling.
The Redis client has no explicit socket connect/read timeout. In this audit,
80 selected backend tests were collected, but the suite stalled at
`test_login_returns_token_and_cookie` until interrupted.

Impact: local/CI results depend on `.env`, DNS, and live services; failures can
hang instead of failing quickly; a developer could accidentally touch a real
account or service.

Required outcome: establish test settings before application import, inject
controlled adapters, prohibit live providers in the default suite, configure
finite client/test timeouts, and add separate explicit integration markers.

### 6. Redis-backed security controls fail open without a declared policy

Evidence: session revocation returns “not revoked” on Redis failure; global and
login rate limiting continue on Redis failure. Several cache methods catch all
exceptions.

Impact: during Redis degradation, logged-out tokens may remain usable until
natural expiry and brute-force/request controls may disappear silently.

Required outcome: threat-model each control, decide fail-open/fail-closed
behavior, make degradation observable, shorten or rotate affected sessions as
appropriate, and test dependency failure explicitly.

### 7. Cross-system writes lack a durable consistency mechanism

Evidence: PostgreSQL mutations and Meilisearch/Qdrant/Celery/Dropbox operations
are separate best-effort calls. The knowledge-core work improves ownership but
does not create atomic delivery.

Impact: commits can succeed while indexing or task publication fails, leaving
stale search results or permanently pending documents.

Required outcome: define idempotency keys and introduce an outbox/reconciliation
path for durable side effects. Add drift metrics and repair commands.

### 8. Production configuration can remain in development mode

Evidence: compose uses `${APP_ENV:-development}` and the production override
does not force `APP_ENV=production`. Several security controls are conditional
on that value.

Impact: a production-shaped deployment with a missing variable can retain dev
CORS defaults, non-secure cookie behavior, introspection, verbose SQL logging,
weaker secret checks, and disabled global rate limiting.

Required outcome: make the production deployment manifest set production mode
unconditionally and add a startup/deployment smoke test for security settings.

## P2 — maintainability and maturity

### 9. Large files concentrate unrelated responsibilities

Examples at audit time:

- `frontend/src/App.tsx`: 1,377 lines.
- `backend/app/graphql/schema.py`: 1,006 lines.
- `frontend/src/components/SpecialistDossierPane.tsx`: 935 lines.
- `backend/app/services/crew_query.py`: 708 lines.
- `backend/app/services/cv_table_extractor.py`: 690 lines.
- `backend/app/services/cv_processing.py`: 596 lines.

Impact: ownership is unclear, changes collide, tests become broad, and AI edits
are more likely to create inconsistent local patterns.

Required outcome: extract cohesive use cases/components gradually, with
characterization tests and no behavior-changing “big bang” rewrite.

### 10. Layer boundaries are only partially established

Evidence: GraphQL resolvers perform queries and commits; API modules open
sessions directly; services create their own sessions; `sync_processor.py`
maintains a second synchronous engine; global client singletons are common.

Impact: transaction ownership, dependency failure, tests, and reuse are harder
to reason about.

Required outcome: move use-case orchestration into services, pass explicit
sessions/ports, converge on one database lifecycle, and enforce import rules.

### 11. Frontend quality gates are stronger locally than in CI

Evidence: local scripts provide unit tests, strict UI audit, and Playwright, but
CI runs only type checking, build, and `npm audit`. `npm ci || npm install` also
allows CI to fall back to a non-reproducible dependency resolution.

Audit result: type check, 46 Vitest tests, production build, and strict UI audit
passed. The build warned that the main application chunk is approximately
371 kB minified, and the UI audit emitted 23 metadata-text-size warnings.

Required outcome: use `npm ci` only, add unit/UI/E2E gates to CI, review the 23
warnings, and introduce a deliberate bundle budget/code-splitting policy.

### 12. Runtime and development dependencies are mixed

Evidence: `pytest` and `pytest-asyncio` are pinned in runtime requirements,
while required test driver `aiosqlite` is missing. Ruff, mypy, Bandit, and
pip-audit are installed ad hoc in CI.

Impact: production images are larger while developer/CI environments remain
non-reproducible.

Required outcome: define locked runtime and development dependency groups and
build production images from runtime dependencies only.

### 13. “Latest” infrastructure tags reduce reproducibility

Evidence: Qdrant and Ollama use `latest` image tags.

Impact: rebuilds can change behavior without a reviewed source change.

Required outcome: pin reviewed versions or digests and update through a tested
dependency process.

### 14. Canonical field values are still manually synchronized

Evidence: `backend/app/domain/fields.py` states that domain tuples and GraphQL
enums remain separate sources that require manual synchronization.

Impact: accepted values can drift between ingestion, storage, search, and API.

Required outcome: derive transport enums/validation from one owned vocabulary
where practical and add contract tests where representation must differ.

## What is working well

- The new `app/domain` vocabulary and `ConsultantKnowledgeService` reduce
  duplicated retrieval/normalization paths.
- Semantic search remains feature-flagged after evidence showed the local model
  and dataset were not ready.
- Upload security has focused regression tests for magic bytes and path
  traversal.
- GraphQL depth validation and production introspection control are present.
- Session cookies are HttpOnly and Secure in production mode.
- Containers use a non-root runtime user and production compose hides internal
  ports.
- Alembic revisions form a single linear chain through revision 012.
- Frontend type checking, unit tests, build, and automated UI inspection pass in
  the current working tree.

## Recommended remediation sequence

1. Decide repository topology and make clean-checkout CI real.
2. Separate migration execution from app startup and remove production
   `create_all` fallback.
3. Repair deterministic backend/frontend CI and test isolation/timeouts.
4. Define and test the authorization matrix.
5. Harden production-mode configuration and Redis security degradation.
6. Add durable side-effect delivery/reconciliation.
7. Enforce import boundaries and decompose large files incrementally.
8. Add PostgreSQL integration, contract, coverage, bundle, and operational
   readiness gates.

## Verification performed during this audit

- Inspected both Git working trees and existing documentation/configuration.
- Reviewed service topology, imports, API authorization decorators, database
  lifecycle, migrations, test setup, and CI.
- Confirmed one linear Alembic head chain through revision 012 by inspection.
- Frontend: TypeScript check passed; 46 unit tests passed; production build
  passed with a bundle warning; strict UI audit passed with 23 warnings.
- Backend: 82 tests collected, 2 marked LLM tests deselected, then the first
  auth test stalled on the current local configuration and the run was
  interrupted. Ruff and mypy executables were not installed in the backend
  virtual environment, so those gates were not run locally. This is recorded
  as an environment/quality-system failure, not as a code-test failure.
